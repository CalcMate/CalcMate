## B. 차기 적용 권장 (설계, 미적용)

### B-1. SQLite 로컬 캐시 + 백그라운드 동기화 (첫 진입까지 단축) — ✅ 적용 완료(2026-06-22)
구현: `modules/dashboard_cache.py`(미러 read/refresh/invalidate), `dashboard.py` 2단 캐시 연동, `scripts/sync_cache.bat` 워밍.
- 미러 우선 읽기(~6ms), 미스/만료 시 원본 1회 조회→갱신, **원본 오류 시 미러 폴백**(시트 403에도 무크래시).
- 액션 후 자동 invalidate로 신선도 유지. 주기 워밍(sync_cache.bat) 시 첫 진입도 즉시.
- 검증: 콜드/웜/출력동일/오류폴백 전부 통과. (아래는 원설계 메모)


현재 캐시는 첫 진입 1회는 여전히 Sheet 왕복(5.7초). 이를 없애려면 **로컬 SQLite를 읽기 캐시로** 두고, 백그라운드가 주기적으로 Sheet→SQLite 동기화.

```
[Dashboard]  ──읽기(빠름)──▶  [SQLite 캐시]  ◀──주기 sync──  [Google Sheet(원본)]
   (항상 SQLite에서 즉시 읽기)         (run_scheduler/별도 워커가 N분마다 갱신)
```

- 구현: `adapters/db`에 이미 `sqlite_adapter` 존재 → 읽기 전용 미러 DB 1개 추가, 동기화 잡(`--sync` 또는 스케줄러 훅)에서 `sheets→sqlite` 복사.
- 대시보드는 `DB_ADAPTER`를 그대로 두되, **읽기 표시용 cfg만 sqlite로 분기**(쓰기는 sheets 유지) 또는 캐시 레이어가 sqlite 우선.
- 개선 예상치: 첫 진입도 5.7초 → <0.1초.
- 위험요소: 동기화 지연(원본과 수 분 차이), 쓰기-읽기 일관성 설계 필요. **출력 변경 가능성 있어 별도 검증 필수.**

### B-2. 대형 탭 분리 (pages/ 멀티페이지)
`dashboard.py`(1430줄)를 `pages/`로 분리하면 페이지별 스크립트만 실행 → 코드 파싱/초기화 경감.

```
pages/ dashboard_home.py · dashboard_board.py · dashboard_sites.py
       dashboard_publish.py · dashboard_strategy.py · dashboard_settings.py
```

- 효과: 페이지 전환 시 해당 페이지 코드만 실행, import 트리 축소.
- **위험요소(중요)**: Streamlit 멀티페이지는 사이드바 네비게이션 UX가 현재 `st.radio` 단일 페이지 방식과 **다름 → 출력/조작감 변경**. 본 작업의 "출력 변경 금지" 원칙과 충돌하므로 **현 단계 미적용**, 별도 합의 후 진행 권장.
- 대안(출력 유지): 현행 단일 페이지 유지 + 탭별 함수 분리(모듈화)로 가독성만 개선.

### B-3. 불필요한 rerun 최소화
- 현재 `st.rerun()`은 주로 **쓰기 액션 직후 1회**(저장/삭제/상태변경/생성) 사용 — 정당한 패턴.
- 점검 결과 과도한 자동 rerun(루프성)은 없음. 실시간 로그의 `st.fragment(run_every=5)`는 토글로 제어 가능 → 불필요 시 끄면 절약.
- 권장: 위젯 콜백에서 값만 바뀌는 경우 rerun 대신 session_state 사용(이미 일부 적용). 추가 대규모 변경 불필요.
